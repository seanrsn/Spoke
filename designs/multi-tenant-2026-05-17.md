## Problem Statement

The Brooklyn Bikery app is a working, production-grade bike shop service-tracking
system (customer intake → admin service log → auto-priced SMS invoice via Twilio),
running ~100 orders/month for a single shop on AWS serverless infrastructure. Sean
wants to enable multi-tenancy so the same system can serve other bike shops, with
the eventual possibility of selling it as a SaaS to those shops.

The honest framing after the office-hours diagnostic: Sean has not yet validated
demand from any other shop. The motivation right now is "I have a massive head
start and it'd be fun to make this multi-tenant" — explicitly an explore / fun /
portfolio motion, not a committed startup motion. The design needs to leave the
door open to monetization later without forcing the customer-development work now.

## Demand Evidence

**1/10. Self-acknowledged by founder.** No other shop has asked for this. No
named prospects. Existing thesis ("indie shops are priced out of Ascend at ~$200/mo")
is unverified — it might really be price, or it might be migration cost, or
hardware aversion, or sunk cost in their existing POS. Sean has not interviewed
a single other shop owner about their workflow or their reasons for not using
Ascend / Lightspeed.

This is the gating risk for any "real startup" framing. It is NOT a gating risk
for the "fun project / be ready when demand emerges" framing this design adopts.

## Status Quo (Competitive Landscape)

Bike-shop service-tracking software is a mature category with entrenched incumbents:

- **Ascend** (Trek-owned, $99-200/mo) — bike-shop-specific POS, 15+ years of
  feature accumulation, widely deployed.
- **Lightspeed Retail Bike Module** — general retail POS with a bike vertical.
- **Shopify POS / Square** — generic retail POS used by smaller shops without
  bike-specific features.

Brooklyn Bikery has *zero* bike-shop-specific features Ascend doesn't have. Its
real differentiator is "lightweight, mobile-friendly, BYOD" — but that's table
stakes (Ascend runs on iPad, Lightspeed on phone, Square invented BYOD POS).
**The only credible wedge against Ascend is SMS-invoicing (which Ascend handles
poorly) or a segment Ascend doesn't bother with (mobile mechanics).** This wedge
is NOT what this design implements — see "Recommended Approach" below for why.

## Target User & Narrowest Wedge

**Founder's stated target:** Indie bike shops priced out of Ascend / Lightspeed.

**Diagnostic notes:** This is a filter, not a person. No specific named shop
exists yet. Quick TAM math: ~2000 US indie shops × $40/mo × 30% capture = ~$24K
MRR. That's a strong solo-income business, not a VC-fundable outcome. To be
startup-scale would require either (a) higher ARPU with sharper differentiation,
or (b) expansion to adjacent verticals with the same intake→service→invoice
pattern (ski tuning, watch repair, small-engine, mobile detailing, etc.).

This design intentionally does NOT lock in a wedge — multi-tenancy alone is a
horizontal capability that supports any of the above wedges if Sean later
commits to one.

## Approaches Considered

### Approach A: Validate First, Build Second
1 week of customer discovery (cold emails, walk-ins, forum posts) before writing
any code. Decision gate at end of week: 3+ named shops willing to pay → build.
< 3 → kill the project.
- Effort: S (1 week, no engineering)
- Risk: Low
- **Rejected** because Sean explicitly does not want to do the sales work right now,
  and would rather build for fun. This is the recommended approach if Sean ever

### Approach B: Wedge Product (Standalone SMS-Invoice Tool)
Strip out only the SMS-invoice flow as a standalone product running alongside
Ascend/Lightspeed. $20-30/month, sells across verticals (not just bike shops).
- Effort: M (2-4 weeks)
- Risk: Med
- **Rejected** because Sean's goal is "enable multi-tenancy on the existing app,"
  not "build a new narrower product." Worth revisiting if Approach C ships and
  no demand materializes.

### Approach C-lite: Enable Multi-Tenancy on the Existing App (RECOMMENDED)
Refactor the existing single-tenant app to support N tenants in one database via
the shared-DB-with-tenant_id pattern. No billing, no signup, no Stripe, no
marketing site. Sean manually provisions tenants via DB insert.
- Effort: M (1-2 weeks with AI pair-programming)
- Risk: Med (architectural risk, not market risk — market risk is unaddressed by design)

### Approach C-full: Full Self-Serve Multi-Tenant SaaS
Same as C-lite plus Stripe billing, self-serve signup flow, tenant onboarding,
admin tooling, support docs, marketing landing page.
- Effort: L (6-10 weeks)
- Risk: High — 2+ months of building with zero validated demand.
- **Rejected** as premature. Add this scope ONLY after C-lite ships and validates
  that other shops want it.

## Recommended Approach: C-lite

### Architecture: Shared DB + tenant_id columns

Industry-standard multi-tenant SaaS pattern. Single RDS MySQL instance. Every
domain table grows a `tenant_id` foreign key. Every Lambda extracts `tenant_id`
from the authenticated JWT and filters every query by it.

**Why this and not the alternatives:**

- **vs. separate tables per tenant** (`orders_brooklyn`, `orders_acme`): schema
  migrations become hell, queries require dynamic SQL, indexes don't share.
  Don't do this.
- **vs. separate database per tenant**: strongest isolation, but pays per-DB
  cost (~$15/mo minimum per RDS instance) and migrations require N independent
  runs. Overkill for $30/mo SaaS where data sensitivity is low.
- **vs. separate AWS account per tenant**: maximum isolation, used by enterprise
  SaaS (Stripe, Snowflake). Wildly overkill here.

### Schema changes

**New table: `tenants`**
```sql
CREATE TABLE `tenants` (
  `id` int NOT NULL AUTO_INCREMENT,
  `slug` varchar(50) NOT NULL UNIQUE,         -- e.g. 'brooklyn-bikery', used in subdomains/URLs
  `display_name` varchar(100) NOT NULL,       -- 'Brooklyn Bikery'
  `phone` varchar(20) DEFAULT NULL,           -- shop's contact phone
  `address` text DEFAULT NULL,                -- shop address (for invoice footer)
  `twilio_account_sid` varchar(100) NOT NULL, -- per-tenant Twilio creds in Secrets Manager
  `twilio_auth_token_secret_arn` varchar(255) NOT NULL,
  `twilio_from_number` varchar(20) NOT NULL,  -- the SMS sender number
  `sms_sender_name` varchar(50) NOT NULL,     -- e.g. 'Brooklyn Bikery' for branded SMS
  `tax_rate` decimal(5,4) NOT NULL DEFAULT '0.0875', -- 8.75% NYC default
  `allowed_origin` varchar(255) NOT NULL,     -- per-tenant CORS origin
  `admin_password_secret_arn` varchar(255) NOT NULL,
  `jwt_signing_secret_arn` varchar(255) NOT NULL,
  `status` enum('active','suspended') NOT NULL DEFAULT 'active',
  `created_at` timestamp DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `slug` (`slug`)
);
```

**Add `tenant_id` to existing tables:**

- `customers`: `tenant_id INT NOT NULL`, FK to `tenants.id`, drop the existing
  `UNIQUE KEY phone` and replace with `UNIQUE KEY tenant_phone (tenant_id, phone)`
  so the same customer phone number can exist at different shops without conflict.
- `orders`: `tenant_id INT NOT NULL`, FK to `tenants.id`. Composite index
  `(tenant_id, customer_id)` for dashboard queries.
- `payments`: `tenant_id INT NOT NULL`, FK to `tenants.id`. Composite index
  `(tenant_id, id)`.

**Services: flip from columns to rows (PROPOSED, marked for Sean's review).**

The current schema has ~50 boolean columns on `orders` like `front_flat`,
`tune_up`, `replace_chain`, with a parallel `_price` column on `payments`. This
forces every tenant to use Brooklyn Bikery's exact service menu — which defeats
the point of multi-tenancy if any future shop has a different list of services
(e-bike-only shop, mobile mechanic with limited tooling, ski tuning expansion,
etc.).

**Proposed new schema:**

```sql
CREATE TABLE `service_catalog` (
  `id` int NOT NULL AUTO_INCREMENT,
  `tenant_id` int NOT NULL,
  `code` varchar(50) NOT NULL,              -- e.g. 'front_flat', stable for code
  `display_name` varchar(100) NOT NULL,     -- e.g. 'Front Tire Flat Repair'
  `default_price` decimal(8,2) NOT NULL,
  `pricing_formula` varchar(255) DEFAULT NULL, -- for spokes: 'base + 2*count'
  `category` varchar(50) DEFAULT NULL,      -- 'brakes', 'drivetrain', etc. for UI grouping
  `is_active` tinyint(1) NOT NULL DEFAULT '1',
  `sort_order` int NOT NULL DEFAULT '0',
  PRIMARY KEY (`id`),
  UNIQUE KEY `tenant_code` (`tenant_id`, `code`),
  FOREIGN KEY (`tenant_id`) REFERENCES `tenants` (`id`) ON DELETE CASCADE
);

CREATE TABLE `order_services` (
  `id` int NOT NULL AUTO_INCREMENT,
  `tenant_id` int NOT NULL,
  `order_id` int NOT NULL,
  `service_catalog_id` int NOT NULL,
  `quantity` int NOT NULL DEFAULT '1',       -- for spoke counts etc.
  `price_charged` decimal(8,2) NOT NULL,     -- snapshot at time of service
  `notes` varchar(255) DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `tenant_order` (`tenant_id`, `order_id`),
  FOREIGN KEY (`tenant_id`) REFERENCES `tenants` (`id`) ON DELETE CASCADE,
  FOREIGN KEY (`order_id`) REFERENCES `orders` (`id`) ON DELETE CASCADE,
  FOREIGN KEY (`service_catalog_id`) REFERENCES `service_catalog` (`id`)
);
```

`orders` keeps `id, tenant_id, customer_id, date_of_service, bike_description,
customer_notes, backend_notes` and drops all the per-service columns. `payments`
collapses to `id, tenant_id, order_id, subtotal, tax, final_price` and drops all
the per-service `_price` columns. The 50 individual `_price` columns become rows
in `order_services`.

**One-time migration script** copies existing Brooklyn Bikery data into the new
shape: insert a `tenants` row for Brooklyn Bikery, populate `service_catalog`
with the existing 50 services + their default prices from `Backend-Form.py`,
then walk every existing `orders` row and explode each set boolean column into
a corresponding `order_services` row.

**Decision flag for Sean:** if you want a smaller v1 that keeps services as
columns and just adds tenant_id, that's faster (3-5 days vs 1-2 weeks) but bakes
in a long-term limitation. The doc recommends biting the bullet now because it's
cheaper to do this once than retrofit it later, but this is a real fork — push
back if you disagree.

### Code changes (per Lambda)

For each Lambda (`Customer-Form.py`, `Backend-Form.py`, `Admin-Dashboard.py`,
`Send-SMS.py`):

1. **Tenant resolution.** Add a helper `resolve_tenant(event)` that:
   - For public endpoints (Customer-Form), reads tenant slug from the URL
     subdomain or `?tenant=` query param.
   - For admin endpoints (Backend-Form, Admin-Dashboard), extracts `tenant_id`
     from the verified JWT claims.
   - Loads the matching `tenants` row and returns a `Tenant` dict for use
     downstream.
   - Returns 404 if no matching tenant or `status != 'active'`.
2. **Every SQL query gets `WHERE tenant_id = %s`** as the leading filter.
   Add a code review checklist item: "every read/write query filters by
   tenant_id."
3. **Twilio client is constructed per-tenant** from the tenant's
   `twilio_account_sid` + `twilio_auth_token_secret_arn`. Cache per-request,
   not globally.
4. **CORS:** replace hardcoded `ALLOWED_ORIGIN` env var with per-tenant
   `tenant['allowed_origin']` returned in response headers.
5. **JWT:**
   - Option A (simpler): use ONE master signing secret, embed `tenant_id` as a
     claim, every admin auth check verifies the claim.
   - Option B (more isolated): per-tenant signing secret stored in Secrets
     Manager, look up by tenant slug at login.
   - Recommendation: **Option A** for v1. Move to Option B only if a
     compliance need ever shows up.
6. **Tax rate** sourced from `tenant['tax_rate']`, not hardcoded 0.0875.
7. **SMS template** uses `tenant['display_name']` and `tenant['sms_sender_name']`
   in the body; `tenant['twilio_from_number']` is the sender.

### Frontend changes

- **Tenant resolution on page load:** customer-form, backend-form,
  admin-dashboard all detect tenant from `window.location.hostname` (subdomain
  routing — e.g. `brooklyn.spoke.app`, `acme.spoke.app`) OR from `?tenant=slug`
  query param as fallback.
- **Tenant config endpoint:** new public GET `/api/tenant?slug=...` returns
  `{display_name, address, phone, services: [...]}` for the form to render.
  Customer-form needs the services list to render checkboxes dynamically
  instead of having them hardcoded in the HTML.
- **Branding:** display tenant's `display_name` in page title, header,
  invoice footer. Logo/colors out-of-scope for v1 — flat-text branding only.

### Infra changes

- **CloudFront:** add an alternate domain name (CNAME) for `*.spoke.app` (or
  whatever the new SaaS umbrella domain is). For v1, you can run multiple
  tenants on path-based routing of the same domain (e.g.
  `brooklynbikery.com/t/brooklyn` vs `brooklynbikery.com/t/acme`) to avoid
  having to register a new domain.
- **Route 53:** wildcard A-record if using subdomain routing.
- **ACM cert:** wildcard SSL for `*.spoke.app` if using subdomain routing.
- **Secrets Manager:** per-tenant secret entries for Twilio creds, admin
  password hashes, optionally JWT signing keys. Naming convention:
  `spoke/tenant/{slug}/twilio`, `spoke/tenant/{slug}/admin-password`.
- **API Gateway:** no changes needed if using JWT-claim-based tenant routing.
  All existing endpoints continue to work; the Lambdas internally resolve
  tenant from request context.

## Confirmed Decisions (Sean-approved 2026-05-17)

1. **Services schema:** Flip from columns to rows. New `service_catalog` and
   `order_services` tables. One-time backfill explodes existing booleans into
   rows. The 50 `_price` columns on `payments` collapse to a single price snapshot
   on each `order_services` row.
2. **Tenant URL routing:** Path-based on existing `brooklynbikery.com` domain
   (`brooklynbikery.com/t/{slug}`). No new domain registration, no wildcard
   DNS/cert work. Reversible if subdomain routing becomes desired later — the
   tenant-resolution logic abstracts the URL shape.
3. **JWT strategy:** Single master signing secret in Secrets Manager. `tenant_id`
   embedded as a JWT claim. Every admin endpoint reads tenant_id from the verified
   claim.
4. **Tenant provisioning:** `provision_tenant.py` CLI. Takes shop config as args,
   inserts `tenants` row, seeds `service_catalog` from a default-services template,
   creates Secrets Manager entries for Twilio + admin password, prints admin
   login URL + temp password.
5. **Production migration safety:** In-place strangler pattern with RDS
   snapshots before each schema change. Old + new code run in parallel for at
   least one week before any old columns are dropped. RDS snapshot restore is
   the safety net.
